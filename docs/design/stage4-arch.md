# 단계 4 설계 — 실시간 관찰, 시간 되돌리기, 화산

- 작성일: 2026-10-19
- 관련 설계: [evolution-sim-arch.md](evolution-sim-arch.md) (rev 5) 결정 5(이중 시계)·6(관찰 UI)·7(세이브), [stage3a-results.md](stage3a-results.md) §5.4(영구 눈덩이 지구)
- 관련 brief: 별도 brief 없음. 사용자 요구(2026-10-19 대화):
  - "실시간으로 거기서 자라거나 하는 것이 보이는 것" — 바다 전체와 세포 확대 **둘 다**
  - "시점은 언제든지 되돌릴 수 있고" — 되감아 보기와 그 시점에서 다시 실행 **둘 다**

- 상위 설계와의 관계: 상위 설계의 단계 4(관찰 UI, 종 판별·계통수 포함)와 단계 5(세이브·장기 실행) 일부, 단계 6의 화산을 합쳐 다시 나눈다.

## 0. 사실 확인 (2026-10-19 측정)

| 항목 | 값 |
|---|---|
| 전체 상태 크기 | 화학장 8 × 1024 × 384 × f64 = 25 MB, 유전체 124 × f32 × 131,072 = 65 MB, 나머지 개체 필드 약 9 MB, 빛·온도 3 MB → **약 100 MB** |
| 디스크 여유 | 95 GB |
| 처리량 | 5만 마리 412~426 tick/s, 13만 슬롯 번성 상태 406~458 tick/s |
| 슬롯 수 (게이트 10만 tick 시점) | 열수구 세계 2천~1만, 번성 세계 13만(가득) |
| GPU 결정성 | CUDA는 비결정이다. 같은 상태에서 다시 실행해도 다른 역사로 갈라진다 |

## 결정 1. 작업 순서

| 옵션 | 설명 | trade-off |
|---|---|---|
| A. 화면 → 시간 기계 → 화산 | 보이는 것부터 | 눈덩이로 멈추는 세계를 보며 만들게 된다 |
| **B. 화산(4a) → 화면(4b) → 시간 기계(4c) → 종·계통수(4d)** | 과학 → 보기 → 되돌리기 → 분류 | 4a는 작고 세계를 "볼 만하게" 만든다. 4b에서 세포 기록 형식이 정해지고, 4c는 그 형식을 디스크에 쌓기만 하면 된다. 4d의 종 ID는 세포 기록과 기록 파일에 한 필드로 덧붙는다 |
| C. 시간 기계 먼저 | | 기록할 형식(무엇을 그릴지)이 정해지기 전이라 다시 만들 가능성이 크다 |

**추천: B.** 각 하위 단계 끝에 평가 에이전트 판정을 받는다.

## 결정 2. 화산 모델 (4a)

| 옵션 | 설명 | trade-off |
|---|---|---|
| A. 일정한 대기 CO₂ 원천 | 매 tick 같은 양 | 가장 단순하다. 기후 사건의 "우연"이 없다 |
| **B. 포아송 분출 (상위 설계 결정 5)** | 평균 빈도 λ로 분출하고, 분출마다 대기에 CO₂(와 환원제 R 소량)를 넣는다 | 설계 원안 그대로다. 큰 분출이 해빙의 방아쇠가 될 수 있다 |
| C. 열수구 CO₂의 일부를 대기로 돌림 | 총 공급량 불변 | 기후 평형을 덜 건드린다. 육상·해상 화산이 따로 없다는 점에서 덜 현실적이다 |

**추천: B.** 평균 공급량을 열수구 CO₂(0.8/tick)와 같은 크기로 두고, 풍화 계수를 올려 현재 평형 온도(약 7~9°C)를 유지한다.
- 눈덩이 탈출 시간 추정: 결빙 중에는 풍화가 0이라 대기 CO₂가 평균 공급량만큼 쌓인다. 해빙 문턱(pCO₂ 약 2.3)까지 약 1.9e5가 필요하므로 약 24만 tick이다(**추정**). 압축 1:1000이면 2억 4천만 년으로, 실제 휴로니안 빙하기(약 3억 년)와 같은 규모다.
- 수지: 화산 CO₂는 `SRC_C`, 환원제는 `SRC_E`에 기록한다. 분출 시점은 시뮬레이션 RNG로 정한다(각본 아님).

**예상 리스크**
- 풍화 재조정 후 S4가 바뀔 수 있다. 4a 게이트에서 다시 잰다.
- 테스트: 결빙 상태에서 화산만으로 해빙되는지(CO₂ 강제 없이) 확인한다. 단계 1 히스테리시스 테스트는 강제를 썼으므로 근거가 되지 않았다.

## 결정 3. 화면 구성 (4b)

| 옵션 | 설명 | trade-off |
|---|---|---|
| A. 서버가 전부 이미지로 렌더 | 지금 방식 확장 | 확대하면 픽셀만 커진다. 세포 하나의 성장·분열이 보이지 않는다 |
| **B. 바다 전체는 서버 GPU 이미지, 확대 화면은 브라우저가 세포 기록으로 직접 그림** | 확대 영역의 세포 목록(위치, 크기, 색, 종류, uid, 부모 uid)을 보내고 브라우저 Canvas가 그린다 | 부드러운 확대와 움직임이 가능하다. uid로 프레임 사이 위치를 보간하고, 새 uid가 부모 옆에 나타나면 분열로 그린다. 확대 영역의 세포 수(수천 개)만 보내면 되므로 가볍다 |
| C. 전부 브라우저 WebGL | 13만 개를 브라우저가 그림 | 매 프레임 수 MB를 보내야 한다 |

**추천: B.**
- **바다 전체 (현실적 색)**: 모두 실제 장 값에서 나온다.
  - 물 색 = 빛 감쇠(표층 청록 → 심해 남흑)
  - 열수구 = 온도장 발광
  - 얼음 = 결빙률만큼 수면 흰 층
  - 산소·메탄 = 선택 시 옅은 안개
  - 생물 점 = 형질에서 나온 색소
- **색소 색**: 형질에서 계산한다. 광합성 η → 엽록소 녹색, 비산소 광합성 → 갈자색(실제 녹색황세균·자색세균 계열), 화학합성 → 무색에 가까운 회백색, 포식 → 투명한 연갈색. 계통 색 유전자는 같은 색 안에서 명도·채도만 조금 바꾼다. 실제 미생물의 색 계열이며, 데이터에 없는 것은 그리지 않는다.
- **확대 화면**: 세포 지름 ∝ (세포 몸)^(1/3). 막 테두리, 색소, 헤엄 방향은 짧은 꼬리(실제 이동 벡터)로 그린다. 분열은 부모에서 갈라져 나오는 애니메이션, 죽음은 흐려짐으로 그린다. 묶음(ncell > 1)은 "세포 n개 군체"로 겹쳐 그리고 숫자를 표시한다.
- **시간 척도 표시**: 확대해서 볼 때는 배속을 "관찰 속도"(프레임당 1~5 tick)로 자동으로 낮출 것을 제안하는 버튼을 둔다. 최대 배속에서는 프레임 사이에 수백 tick이 지나 성장이 보이지 않는다. 1 tick = 1,000년 표기는 그대로 두되, 확대 화면에는 "생물 tick"을 함께 보인다(상위 설계 결정 5 이중 시계).

**예상 리스크**
- 렌더가 시뮬레이션 시간을 먹는다. 바다 전체 이미지는 GPU 커널로 만들고, 세포 목록은 확대 영역만 뽑는다(GPU에서 영역 필터 → 작은 배열만 복사).

## 결정 4. 되감아 보기 기록 (4c)

| 옵션 | 설명 | trade-off |
|---|---|---|
| A. 렌더된 영상 프레임만 저장 | PNG/WebP 연속 | 되감아서 확대할 수 없다 |
| **B. 프레임 기록 = 바다 전체 이미지 + 전체 세포 기록 + 통계** | 세포 기록은 슬롯당 약 20 B(위치 u16 × 2, uid·부모 하위 32비트, 세포 크기·n f16, 색소 RGB, 종류 플래그)를 zlib으로 압축 | 되감은 시점에서도 확대·이동·분열 애니메이션이 된다. 화면 스타일을 나중에 바꿔도 기록을 다시 그릴 수 있다 |
| C. 전체 상태 스냅샷만 | 약 100 MB/개 | 촘촘히 저장할 수 없다 |

**추천: B.**
- 간격: 최근 구간은 100 tick마다 기록한다.
- 크기: 열수구 세계(5천 슬롯)는 기록 1개에 약 100 KB, 번성 세계(13만 슬롯)는 약 1.5 MB다(**추정**, 압축률 0.6 가정).
- 되감아 보기 화면은 실시간 화면과 같은 렌더러를 쓴다. 데이터 출처만 다르다.

## 결정 5. 그 시점에서 다시 실행 (4c)

| 옵션 | 설명 | trade-off |
|---|---|---|
| **A. 전체 상태 스냅샷 + 갈래** | 1만 tick마다 전체 상태(약 100 MB, 압축)를 저장한다. 사용자가 시점을 고르면 그 이전 가장 가까운 스냅샷을 불러 새 갈래로 실행한다 | 정확한 상태에서 다시 시작한다. 스냅샷 사이의 시점은 가장 가까운 앞 스냅샷으로 맞춘다 |
| B. CPU 결정 모드로 처음부터 재연 | 같은 seed로 CPU 단일 스레드 재실행 | 정확히 같은 역사가 나오지만 수십 배 느려서 실시간 관찰에 쓸 수 없다 |
| C. 세포 기록에서 상태 복원 | 프레임 기록만으로 재시작 | 유전체·화학장이 없어 불가능하다 |

**추천: A.**
- 갈래는 트리로 관리한다. 같은 시점에서 여러 번 다시 실행할 수 있고, 각 갈래는 자기 기록을 갖는다.
- UI에 "다시 실행하면 GPU 특성상 다른 역사로 갈라집니다"를 표시한다.

## 결정 6. 저장 예산과 보존

| 옵션 | 설명 | trade-off |
|---|---|---|
| A. 전부 보존 | | 번성 세계 100만 tick이면 프레임 기록만 15 GB, 스냅샷 10 GB |
| **B. 예산 + 오래될수록 성기게** | 기본 예산 20 GB(설정 가능). 넘으면 오래된 구간부터 기록을 하나 걸러 지운다(100 → 200 → 400 tick 간격). 스냅샷도 같은 방식으로 성기게 한다. 최근 구간과 각 갈래의 분기점은 지우지 않는다 | 최근은 촘촘하고, 오래된 과거도 성기게나마 끝까지 남는다 |
| C. 고정 길이 링 버퍼 | 최근 N개만 | 오래된 과거로 돌아갈 수 없다 |

**추천: B.** 저장 형식은 `.npz`(압축) + JSON 메타다(상위 설계 결정 7). `schema_version`을 넣는다.

## 결정 7. 실행 구조

| 옵션 | 설명 | trade-off |
|---|---|---|
| **A. 프로세스 하나: 메인 스레드 시뮬레이션 + HTTP 스레드 + 기록 쓰기 스레드** | Taichi 호출은 메인 스레드에만 둔다. 메인이 GPU에서 numpy로 복사하고, 압축·쓰기는 쓰기 스레드가 큐로 받는다 | 지금 뷰어 구조를 확장한다. 단일 스레드 Taichi 규칙을 지킨다 |
| B. 시뮬레이션과 뷰어를 별도 프로세스로 | 디스크 기록을 공유 | 구현량이 두 배다. 실시간 확대 화면에 지연이 생긴다 |

**추천: A.**
- 되감아 보는 중에도 시뮬레이션은 계속 앞으로 간다(일시정지는 선택).
- "다시 실행"은 현재 갈래를 멈추고 스냅샷을 불러 새 갈래로 바꾼다.

## 결정 8. 종 판별과 계통수 (4d, 사용자 요청으로 이번 단계에 포함)

| 옵션 | 설명 | trade-off |
|---|---|---|
| **A. 주기적 표본 군집 (상위 설계 결정 6)** | 2,000 tick마다 유전체를 최대 1만 개 CPU로 뽑는다. 형질 유전자(뇌 제외, 범위로 정규화한 거리)로 리더-팔로워 군집을 만든다. 이전 종 중심과 가까우면 ID를 잇고, 아니면 신종으로 만들고 가장 가까운 이전 종을 부모로 기록한다 | 설계 원안이다. GPU 부담이 없다. 종 경계 문턱이 결과를 좌우한다 |
| B. 계통(uid·부모) 추적으로 종 정의 | 실제 조상 관계로 묶는다 | 정확한 조상 관계를 얻는다. 모든 출생을 기록해야 해서 저장량이 매우 크다 |
| C. 군집 + 조상 표본 | A에 부모 uid 표본을 더해 부모 종 판정을 보강 | 정확도는 조금 낫다. 구현이 늘어난다 |

**추천: A.** 종 문턱은 설정값으로 두고 기본값은 4d에서 정한다(상위 설계 결정 6의 리스크).
- 세포 기록에 종 ID를 덧붙여 화면에서 종별로 색을 칠하거나 강조할 수 있게 한다.
- 계통수 화면: 시간 축 위에 종의 수명(출현~소멸)을 막대로, 분기를 선으로 그린다. 막대 굵기는 그 종의 세포 수다. 종을 누르면 대표 형질(대사 방식, 크기, 속도)과 그 종이 있는 위치를 확대 화면에서 강조한다.
- 계통수는 기록 파일에 같이 쌓는다. 되감기와 갈래에서도 그 시점까지의 계통수가 나온다.

## 통과 기준

| 하위 단계 | 기준 |
|---|---|
| 4a 화산 | 결빙 세계가 강제 없이 해빙되는 테스트, 수지 < 1e-9, 평형 온도 유지(±2°C), S4 다시 측정, 기본 10 seed 중 영구 눈덩이로 10만 tick이 끝나는 비율 기록 |
| 4b 화면 | 확대 시 세포 성장·분열·이동·포식이 실제 데이터로 보인다(스크린샷), 화면 요소마다 출처 장·형질이 있다, 렌더 켠 상태 처리량 측정 |
| 4c 시간 기계 | 기록을 되감아 임의 시점을 열고 확대할 수 있다, 스냅샷 왕복 후 상태가 같다(CPU, 비트 단위), 갈래 실행이 동작한다, 예산 초과 시 성기게 하기가 동작한다 |
| 4d 종·계통수 | 단위 테스트(같은 유전체 → 같은 종, 문턱 넘는 변이 → 신종과 부모 기록), 실제 실행에서 UI로 종 분기가 보인다(상위 설계 단계 4 기준) |
